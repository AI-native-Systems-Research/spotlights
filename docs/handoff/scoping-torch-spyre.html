Early work
This is an initial result, not a validated estimator. It is here to show what the idea is — costing a run before you pay for it — and the numbers should be read as an order of magnitude with a ceiling, not as a quote. The accuracy we have measured so far is stated plainly below; it is not good, and this report is written so you can see how far off it can be.

The target

A good fit for the tool

torch-spyre is the PyTorch device-enablement layer for the IBM Spyre accelerator — a C++ and Python codebase whose centre of gravity is _inductor: compiler codegen, scratchpad allocation, and weight-stationary scheduling. That is performance-critical code by construction, which is exactly the material Spotlights is built to read.

It is also a small repository by the standards of this corpus: 80,000 lines of product code, against RocksDB's 478,000 and vLLM's 470,000. That matters in both directions, and the two effects pull against each other — few modules to pay for, but unusually large ones.

Scope

What the extractor actually returned

The advisor takes one input: the in-scope module count. That comes from step 1 of the pipeline, which is a single repo-wide LLM pass. We ran it. It kept three modules.

A cheap structural proxy got this badly wrong

Before paying for step 1 we approximated the module count from directory structure — count source directories above a size threshold. That method returned 7 to 10 modules depending on the threshold, and would have had us quote a ceiling of $270–$385 instead of $116. It over-counted by a factor of 2 to 3.

The reason is that a module is a coherent unit of behaviour, not a directory over a size threshold. The extractor folded the entire _inductor subtree — wsr, scratchpad, codegen and the rest — into one module, and dropped the small directories the proxy had counted. $1.35 for step 1 is worth paying; guessing the module count is the one shortcut that does not survive contact with the real thing.

One consequence worth flagging before you run: _inductor is 78% of the product code in a single module. Spotlights costs and reports per module, so that one module will dominate both the bill and the findings, and there is no way to buy a smaller slice of it through --include.

The labels are the point. measured means observed on real runs with the setting as the only difference. derived means arithmetic on measured inputs. unvalidated means the direction is known and the magnitude is a guess — one row, flagged so nobody plans around it.

Two rows need reading carefully. Capping findings at 20 does nothing: the observed yield is 14 findings per candidate, already under the cap, so the knob is inert until pushed below the natural yield. And the --no-deep-research band is not a subset of the default band — its low end sits above the default's. That row is anchored on its own measured runs with deep research off, of which there are only two, so its band is narrow because the evidence is thin, not because the outcome is more certain.

Reality check

Where in that band to expect it

A band from $5 to $116 is honest but not much use for a budget conversation. The corpus can narrow it, informally. torch-spyre's three modules average 26,700 lines each — against a corpus median nearer 2,800. Only RocksDB is coarser, and it is the most expensive run we have.

Bracketing torch-spyre between vLLM and RocksDB gives 16–35M tokens per module, so 49–104M tokens, or roughly $55–$116 for the full pipeline. Note where that lands: the top third of the band, with its upper edge essentially at the ceiling. If instead it behaves like the corpus median it would be nearer 20M tokens and $22.

How much weight this carries

Not much, and it should be labelled that way in the meeting. The size-to-cost relationship is a rank correlation of 0.53 over 14 runs — a real signal, far from a model. It would sit at unvalidated on the ladder above. Treat $55–$116 as the number to plan against and --max-cost 116 as the number that protects you if it is wrong.

Accuracy

How often this is wrong, measured

The advisor was backtested by removing each repository from the calibration in turn and re-estimating it. That is the fair test, and the results are unflattering on purpose:

Band constructionCoverageWidthMidpoint error
observed min–max (shipped)83%23.2×80% median
p10–p9058%5.3×80% median

The wide band earns its width: it contained 10 of 12 held-out runs. The narrow one looks more useful and contained only 7, which is worse than being vague. RocksDB is the clearest miss — held out, the advisor predicted 25–113M tokens and the truth was 276M.

The reason is not a modelling failure to be fixed. Tokens per module spans 23× across repositories, and the module count — the only input — cannot narrow that. Even five identical replicate runs of one repository varied by 7.7%. So the tool is built to rank settings, which it does well, and to refuse to forecast a price, which it cannot.

Calibration: 18 runs, 8 repositories, 6 engine versions. Eight repositories is not many, and this is the part that should improve fastest as we accumulate runs with their configuration recorded.

Recommendation

What to actually do

  1. Set the ceiling before the first run.

    --max-cost 116. Note it is enforced at step boundaries, not as a hard cap — a measured run with --max-cost 15 finished at $20.20 because the last step started while there was still headroom. Size it below your real limit.

  2. Buy a cheap look first.

    Run with --no-deep-research — $13–$19 and well under an hour. Read the candidates. If they are weak on this codebase you have learned that for a sixth of the price. Note this is not "candidates only": step 5 still runs on every candidate at roughly $0.86 each, which is where most of that money goes.

  3. Expect _inductor to be the whole story.

    One of the three modules holds 78% of the product code. Excluding the other two would save little and lose the device-registration and C++ runtime paths, so scope everything — but read the report expecting the findings to concentrate in one place.

  4. Plan for the clock as well as the bill.

    At 3 modules, expect 1–25 hours of API time, which is 0.2–4.6 hours of wall clock at the historical median concurrency of 5.4×. Concurrency is yours to set; the corpus has run as high as 13.6×.

  5. Re-use the extraction.

    Step 1 has already been paid for. Copying project_tree.json and extractor_invocation.json into a fresh run's artifacts directory makes the orchestrator recover them from disk, so no later run on this commit needs to pay the $1.35 again.

Reproduce

One paid step, then free arithmetic

The first command is step 1 of the real pipeline — it is what produced the module count above, and it is the only thing on this page that cost money. The second makes no API call at all.

$ spotlights-engine --repo ./torch-spyre --max-cost 0.01 \
      --artifacts-dir ~/runs/torch-spyre/artifacts

The --max-cost 0.01 stops the run at the first step boundary after extraction, which is how step 1 was bought without paying for discovery. The calibration stores tokens, never dollars — pricing is a rate-table lookup applied at estimate time, so a contract change does not invalidate the history. At the contracted rate of $0.85/MTok rather than list, every figure on this page falls by about 24%: the $55–$116 planning number becomes $42–$88.
