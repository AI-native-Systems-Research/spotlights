# Generate `repo_context.md` for Stage-1 Candidate Discovery

You are a deep-research agent operating over the web. Your task is to produce
the contents of ONE markdown document, `docs/repo_context.md`, for the
**target GitHub repository specified by the caller** (URL or `owner/repo`).
That document gives a downstream LLM agent the **repo-level** context it
needs to identify good evolutionary code-optimization candidates inside any
module of that repo.

You do not have a local checkout. Do your work by reading the target repo
directly on GitHub:

- Resolve the default branch and tip SHA via the GitHub API (e.g.
  `GET /repos/{owner}/{repo}`, then
  `GET /repos/{owner}/{repo}/commits/<branch>`).
- Read files via the Contents API or `raw.githubusercontent.com` at that
  resolved SHA.
- Search for symbols, commands, and file references via GitHub code search
  scoped to the repo. Treat code-search hits as leads, not as proof — always
  reopen the cited file at the resolved SHA before writing the claim down.

The downstream consumer is the Stage-1 discovery agent in `spotlight-engine`:
it runs as a non-interactive subprocess inside a checkout of the target repo,
is already given a single `Module` to audit (path, description, dependencies,
main files), and is asked to emit candidates that each name:

1. a correctness oracle (a test, golden, property, or invariant),
2. an `estimated_impact` rating (`high`, `medium`, or `low`),
3. an `estimated_impact_explanation` that names the workload-level signal a
   better implementation would move and why the code has headroom.

The Module-level context is supplied separately. Your output must cover what is
**true of the repo as a whole** — the things the agent would otherwise have to
rediscover on every iteration of every module.

## Strict output rules

- Emit exactly ONE markdown document as your final answer, wrapped in a single
  fenced code block with the language tag `markdown` (i.e. opened by three
  backticks followed by `markdown` and closed by three backticks on their own
  line). The block's contents are the literal file body for
  `docs/repo_context.md`; the caller saves it. Emit no other prose, preamble,
  or trailing commentary outside the block.
- Inside the document, use **inline code only** (single backticks) for paths,
  commands, and identifiers. Do NOT use triple-backtick code fences anywhere
  inside the body — they would collide with the outer fence the caller's
  tooling expects, and would also break inlining into the Stage-1 prompt. If
  a command genuinely needs multiple lines, join it onto one line or describe
  it in prose.
- Keep the document under ~5 KB. Concision matters; this text is inlined into
  every Stage-1 prompt.
- Begin the document with a single provenance line of the form
  `<!-- Generated YYYY-MM-DD from <short SHA> (<branch>) -->`, e.g.
  `<!-- Generated 2026-05-16 from a1b2c3d (main) -->`. Resolve the values
  this way:
  1. `YYYY-MM-DD` is today's date in UTC.
  2. `<branch>` is the repo's default branch, read from `.default_branch` in
     `GET /repos/{owner}/{repo}`.
  3. `<short SHA>` is the first 7 hex chars of that branch's tip, read from
     `.sha` in `GET /repos/{owner}/{repo}/commits/<branch>`.
  Treat the snapshot as clean — do not emit `uncommitted`. This provenance
  line is the only allowed HTML.
- Every concrete claim (paths, commands, file names) must be **verified by
  reading the actual repo on GitHub** — open the relevant file at the resolved
  SHA, or confirm path existence via the Contents or Git Trees API at that
  SHA. Do not invent benchmark scripts, test directories, or CI commands that
  aren't actually present.
  If a CI command appears in a README but no corresponding workflow / Makefile
  target / script exists, treat it as unverified and omit it.
- For every required section below, always emit the section header. If you
  have no honest answer, use the exact fallback line specified for that
  section; if the section has no specific fallback, use the single line
  `_(none found in this repo)_`. Empty is better than invented. (Section 9 is
  optional and may be omitted entirely.)
- No marketing language, no philosophy, no aspirations. Only what is true now
  and useful for picking optimization candidates.
- Markdown only after the required provenance comment; no other HTML, no emoji.

## Required sections (in this order)

### 1. Purpose

One short paragraph (2–4 sentences): what this repository is, what runs in
production, who runs it. The point is to let the agent judge "real headroom"
claims — a research notebook and a serving binary have very different
optimization surfaces.

### 2. Languages, runtimes, hard constraints

Bulleted list of the **load-bearing** ones:
- Primary language(s) and version pins (e.g. `Python >= 3.11`, `Go 1.22`,
  `CUDA 12.4`).
- Hardware assumptions baked into the code (e.g. "requires NVIDIA GPU, Hopper
  or later", "x86_64 only", "assumes AVX-512").
- Anything that constrains an evolved variant (e.g. "must remain
  pure-Python-importable", "no new C-extension dependencies").

### 3. Repository layout

State the layout convention the agent will be navigating. Stage 1 candidates
are repo-root-relative paths that must resolve under `module.path`; getting
the layout wrong invalidates every candidate.
- Source root (e.g. `src/` for src-layout, or `./` for flat).
- Test root and whether it mirrors the source tree.
- Any generated/derived directories the agent must avoid editing the output
  of (e.g. `gen/`, `_pb2.py`, `*.generated.go`).

### 4. How tests are run

Cover only what an evolved variant must satisfy:
- The single command a CI run uses to execute the unit-test suite (e.g.
  `uv run pytest tests/unit`).
- Integration-test command if there is one, and whether it is gated (markers,
  env vars).
- Test-framework conventions worth knowing (e.g. fixtures in `conftest.py`,
  marker meanings).
- Coverage / quality gates that must stay green on a PR.

### 5. Benchmarks and performance harnesses

This is the most important section for Stage 1. List the *actual* scripts and
fixtures the agent can cite in a candidate's impact explanation and
correctness rationale. Harnesses come in two flavors — **in-repo** and
**external** — and you must cover both.

#### 5a. In-repo harnesses

Scripts and fixtures that live inside the target repo itself. For each, one
bullet:
- Path (e.g. `benchmarks/decode.py`).
- What it measures, in one phrase (e.g. "decode-step latency at batch size 32").
- How to invoke it (the exact command, including required flags).
- The metric name and unit it emits (e.g. `decode_step_latency_ms`).

If none, use the global "none" fallback under this subheader.

#### 5b. External harnesses

Many projects keep performance harnesses in a *separate* repository (a
companion bench repo, an upstream framework's perf suite, a sibling repo under
the same org, a third-party benchmark suite that targets this project). These
are first-class citations for Stage 1 — list them so the agent can cite them
in impact explanations and measurement recipes instead of inventing a local
harness.

How to find them — try all of these and stop only when you've exhausted the
leads, not on first hit:
- The target repo's README, `CONTRIBUTING.md`, `docs/`, and any
  `benchmarks/README*` for outbound links to a bench repo.
- Same-org siblings whose name suggests benchmarking (e.g. `<repo>-bench`,
  `<repo>-perf`, `<org>/benchmarks`). Verify by reading their README at HEAD.
- CI workflows (`.github/workflows/*.yml`) that `git clone` or
  `actions/checkout` another repo for perf jobs — that repo is an external
  harness.
- Pinned references in `pyproject.toml` / `requirements*.txt` / `go.mod` /
  `Cargo.toml` to a repo that is itself a benchmark suite.
- GitHub code search for the target repo's import path or package name inside
  files named like `bench_*`, `*_bench.*`, `benchmarks/*` across GitHub; treat
  hits as leads and verify each by opening the file.

For each external harness, one bullet using this shape:
- Repo (e.g. `owner/repo-bench`) and path inside it (e.g.
  `suites/decode.py`). Pin to a commit SHA or tag if the README/CI does;
  otherwise say `@HEAD`.
- What it measures, in one phrase.
- How to invoke it end-to-end, including the clone/setup step (e.g.
  `git clone https://github.com/owner/repo-bench && cd repo-bench && uv run python suites/decode.py --target <target-repo-path>`).
  If it needs a checkout of the target repo passed in, say so explicitly.
- The metric name and unit it emits.
- One short note on the *relationship* to the target repo: "official companion
  bench", "upstream framework suite", "third-party — community-maintained".
  This lets the agent weight citations appropriately.

If no external harness exists, write `_(none found)_` under this subheader.

If both 5a and 5b are empty, Stage 1 candidates in this repo will need to
*propose* a harness, and that should be obvious to the agent up front.

### 6. Metric naming and units

Enumerate the metric vocabulary Stage-1 candidates should reuse verbatim. Pull
from two sources:
1. The metric names and units actually emitted by the harnesses you listed in
   section 5 — both 5a (in-repo) and 5b (external). Include any distributional
   suffixes the harnesses report (mean, median, percentile). If an external
   harness uses a different naming convention than the target repo's own
   conventions, list both and note which to prefer.
2. Any unit/suffix conventions documented in the repo itself (CONTRIBUTING,
   style guides, metric-naming docs).

If a harness reports a value in a non-preferred unit, say so and tell the
agent which unit to normalize to. If section 5 is empty AND no documented
convention exists, write
`_(none — agent should encode units in the metric name)_`.

### 7. CI gates an evolved variant must pass

Bullet list of the checks a PR has to clear before merge (lint, type, format,
security scan, license check). Name the tool and the command if it differs
from defaults (e.g. `uv run ruff check`, `uv run mypy src/`,
`uv run pyright`). Skip CI infrastructure detail — only the gates that
constrain code.

### 8. External dependencies that dominate the runtime

Short bullet list of the libraries whose calls are likely to *dominate*
hot-path time (e.g. `torch`, `numpy`, `tokenizers`, `tree-sitter`, `protobuf`).
Only include a dependency when its hot-path role is visible from verified
code, tests, benchmark scripts, or project metadata; do not infer dominance
from a dependency appearing in a lockfile alone.
Mark each with one of:
- `cost-in-deps`: the cost is inside the dep; evolving the wrapper usually
  won't help.
- `cost-at-boundary`: the dep is fast but the way *this* repo calls it
  (batching, dtype, layout, sync) is the headroom.

This helps the agent skip thin wrappers and focus on dispatch / batching /
fusion / sync-elimination patterns the bootstrap prompt already enumerates.

### 9. Repo-wide patterns worth knowing (optional)

Opt-in. Omit the section entirely if nothing here applies. Only include what
would mislead the agent if missed:
- Main hot-path flows: 1-3 named end-to-end paths through modules, each one
  line (e.g. "prefill: tokenizer -> scheduler -> model_executor -> attention
  -> sampler"; "request: ext-proc handler -> director -> scheduling ->
  response"). Include only flows that actually run in production; the point
  is to let the agent judge which modules sit on a hot path and how often
  each step is reached. Cite a verifying source per flow (an entry-point
  file, a top-level handler, or a `main()` function read at the resolved
  SHA); flows must be derivable from the code, not inferred from the README.
- Plugin / registry conventions used across modules (e.g. "all dispatchers
  live in `*/registry.py` and look like `REGISTRY: dict[str, Factory] = {...}`").
- Code-generation steps that mean some files are derived (so candidates should
  target the generator, not the generated file).
- Config-driven runtime knobs that span modules (e.g. a central `tuning.toml`
  whose entries are the natural candidates).

## What to leave OUT

- Per-module detail. The agent is given `Module.description`, `main_files`,
  and `depends_on` separately on every run. Don't repeat them here.
- Architecture / design philosophy. The agent doesn't need to know "why" the
  repo is laid out the way it is, only what to measure and how to verify.
- In-flight work, refactor plans, deprecations. These decay fast and would
  silently mislead future runs. Treat this file as a snapshot of stable state.
- Implementation details inside any one module.
- Anything you cannot verify by reading the repo on GitHub at the resolved
  SHA.

## Final check

Before emitting the code block, re-read your draft and ask: "If I were an LLM
agent that just landed in this repo and had to propose a falsifiable,
measurable optimization candidate inside an arbitrary module, which lines of
this file would I actually use?" Delete the rest. Then emit the single
fenced `markdown` code block — nothing before it, nothing after it — and stop.
