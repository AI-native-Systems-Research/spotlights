## Extended discovery: enrich artifacts from vllm GitHub issues and PRs

After producing the base artifacts above, perform an additional discovery pass against the vllm GitHub repository to find test cases, workloads, and benchmarks that are not present in the local clone but are relevant to KV-cache offloading.

### Step 1 — Search GitHub for relevant issues and PRs

Query https://github.com/vllm-project/vllm using the GitHub CLI (`gh`) or the GitHub REST API. Search for issues and pull requests that are related to KV-cache offloading, CPU offload, disk offload, swap, paged attention, or prefix caching. Suggested queries:

```bash
gh issue list --repo vllm-project/vllm --state all --search "kv cache offload" --limit 50 --json number,title,body,labels,state
gh pr list   --repo vllm-project/vllm --state all --search "kv cache offload" --limit 50 --json number,title,body,labels,state,files
gh issue list --repo vllm-project/vllm --state all --search "cpu offload swap"  --limit 30 --json number,title,body,labels,state
gh pr list   --repo vllm-project/vllm --state all --search "prefix cache evict"  --limit 30 --json number,title,body,labels,state,files
```

Run additional queries as needed to get broad coverage.

### Step 2 — Extract test cases, workloads, and benchmarks

For each issue or PR found, extract the following if present:

- **Test cases**: reproduction scripts, pytest invocations, test file paths referenced in the body or diff (e.g. `tests/kv_cache/`, `tests/distributed/`, inline code snippets that assert specific behavior).
- **Workloads**: model names, dataset references, request patterns, concurrency levels, sequence lengths, or any other workload parameters mentioned (e.g. "128 concurrent requests, seq_len=4096, Llama-2-70B").
- **Benchmarks**: benchmark script invocations (e.g. `benchmarks/benchmark_throughput.py`, `benchmarks/benchmark_latency.py`), reported metric values (throughput, latency, memory), and the conditions under which they were measured.
- **Regression signals**: issues that describe a metric worsening after a change — these become regression checks in the validation plan.
- **Environment constraints**: hardware requirements (GPU model, VRAM, number of GPUs), software versions, or flags that enable/disable the feature under test.

Prefer concrete, runnable entries. Skip items that are purely conceptual or lack enough detail to construct a harness entry or workload config.

### Step 3 — Merge into extended artifacts

Produce three new artifact files under `spotlights-validation/artifacts/kvoffload_extended/`:

**harness_map.json** — start from the base `artifacts/kvoffload/harness_map.json` and add new entries discovered from GitHub. Each new entry must follow the `TestHarnessMap` schema (see design.md). Set `source` to `"github_issue"` or `"github_pr"` and add a `source_ref` field with the URL of the issue or PR it was extracted from. Example entry shape:

```json
{
  "id": "gh_issue_1234_repro",
  "name": "repro — KV offload OOM on long prefix (issue #1234)",
  "kind": "correctness",
  "path": "tests/kv_cache/test_offload_oom.py",
  "invoke": "pytest tests/kv_cache/test_offload_oom.py -v",
  "components": ["kv_cache_manager", "cpu_offload"],
  "output_format": "pytest-json",
  "estimated_duration": 60,
  "source": "github_issue",
  "source_ref": "https://github.com/vllm-project/vllm/issues/1234"
}
```

**workload_matrix.json** — start from the base `artifacts/kvoffload/workload_matrix.json` and add new workload entries extracted from GitHub. Each entry follows the `ValidationWorkloadMatrix` schema. Add a `source_ref` field. Example:

```json
{
  "workload_id": "gh_pr_5678_long_context_70b",
  "workload_class": "long-context",
  "source": "github_pr",
  "source_ref": "https://github.com/vllm-project/vllm/pull/5678",
  "config_path": null,
  "components_exercised": ["kv_cache_manager", "block_manager"],
  "description": "128 concurrent requests, seq_len=8192, Llama-2-70B, CPU offload enabled",
  "parameters": {
    "model": "meta-llama/Llama-2-70B-chat-hf",
    "num_requests": 128,
    "input_len": 512,
    "output_len": 512,
    "max_model_len": 8192,
    "kv_transfer_config": {"kv_connector": "PyNcclConnector"}
  }
}
```

**validation_plan.json** — start from the base `artifacts/kvoffload/validation_plan.json` and add plan entries for the newly discovered harness entries and workloads. Assign priorities using the same rules as design.md: entries that directly exercise the KV offload path get higher priority; entries derived from regression reports get `halt_on_failure: true` when the regression was severe (data loss, OOM crash, correctness failure).

### Constraints

- Do not modify the files under `artifacts/kvoffload/` — only write to `artifacts/kvoffload_extended/`.
- All new artifact files must be valid JSON and conform to the schemas in design.md.
- If a GitHub API rate limit is reached, pause and resume; do not discard partial results.
- If a test path referenced in an issue does not exist in the local `vllm/` clone, still include the entry but set `"path_verified": false`.
- Deduplicate: if an issue or PR references a test that is already in the base harness_map, do not add a duplicate entry — instead annotate the existing entry with the `source_ref`.
- **Version gate (v0.18.0):** Only include entries whose test paths and source code actually exist in the vllm `v0.18.0` tag. Before adding any entry, verify the path with `git ls-tree -r --name-only v0.18.0 <path>` against the local `vllm/` clone. If the path does not exist in `v0.18.0` — even if it exists on `main` — omit the entry entirely. Do not set `path_verified: false` as a workaround for a version-gating failure; that flag is only for paths that are expected to exist but couldn't be confirmed due to network or access issues. Issues and PRs merged after the v0.18.0 release (tag date: check with `git log v0.18.0 -1 --format=%ci` in the vllm clone) are out of scope unless their test file was already present in `v0.18.0`.
