## Findings (full list)

1. **InferCept: Efficient Intercept Support for Augmented Large Language Model Inference**
   - Source type: paper
   - URL: <https://proceedings.mlr.press/v235/abhyankar24a.html>
   - Technique: Adopt an interception/resume model for agentic tool calls: pause generation while an external action runs, retain the request state/KV context, append the tool result, and resume instead of submitting a fresh request. This directly targets multi-turn agentic TTFT by avoiding repeated prefill after every tool boundary.
   - Evidence: Quote: "supporting the efficient interception of LLM generation". Pointer: Abstract, PMLR page.
2. **[Feature]: Add tokenizer process pool to eliminate preprocessing bottleneck · Issue #25301 · vllm-project/vllm**
   - Source type: issue
   - URL: <https://github.com/vllm-project/vllm/issues/25301>
   - Technique: Parallelize front-end preprocessing and output decoding through a tokenizer/preprocessor process pool, especially for long or multimodal inputs. This could reduce media-heavy TTFT by keeping GPU work from waiting behind serialized CPU tokenization, image/video parsing, and decoding work.
   - Evidence: Quote: "A multiprocessing-based tokenizer process pool can be utilized to parallelize the encoding and decoding steps". Pointer: issue body, feature/motivation section.
3. **SMG: The Case for Disaggregating CPU from GPU in LLM Serving**
   - Source type: blog
   - URL: <https://vuink.com/post/clgbepu-d-dbet/blog/lightseek-smg>
   - Technique: Move CPU-bound serving work such as tokenization, detokenization, stop checks, tool parsing, and multimodal preprocessing out of the GPU engine hot path into a Rust/gRPC gateway or equivalent non-GIL service. This targets both TTFT and TPOT when the engine front-end/output processor becomes the bottleneck under concurrent agentic traffic.
   - Evidence: Quote: "tokenization and detokenization had become bottlenecks". Pointer: section "How It Started: Hitting the GIL Wall at Scale".
4. **DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving**
   - Source type: paper
   - URL: <https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin>
   - Technique: Separate prefill and decode execution into independently provisioned worker pools and coordinate them according to TTFT/TPOT SLOs. The engine/coordinator layer could adapt this phase split to prevent long prefills from degrading median TPOT while sizing prefill capacity for lower TTFT.
   - Evidence: Quote: "assigns prefill and decoding computation to different GPUs". Pointer: USENIX abstract.
5. **Disaggregated Serving | NVIDIA Dynamo Documentation**
   - Source type: docs
   - URL: <https://docs.dynamo.nvidia.com/dynamo/design-docs/disaggregated-serving>
   - Technique: Use an explicit prefill-router/decode-router handoff: route to a prefill worker, return transfer metadata, inject it into the decode request, and overlap or accelerate KV movement with NIXL. This is a concrete orchestration design for reducing prefill/decode interference in the engine layer.
   - Evidence: Quote: "Dynamo leverages NIXL to transfer KV cache directly from the VRAM of the prefill engine". Pointer: Design Docs, "Efficient KV Transfer".
6. **Configuration and Tuning | NVIDIA Dynamo Documentation**
   - Source type: docs
   - URL: <https://docs.nvidia.com/dynamo/latest/components/router/configuration-and-tuning>
   - Technique: Adopt KV-overlap-aware worker scoring with tunable TTFT-vs-ITL weighting, prompt-side load accounting, and router queue policies such as WSPT for average TTFT. This could replace or augment count-based data-parallel routing in the engine client/coordinator.
   - Evidence: Quote: "Higher values improve Time To First Token (TTFT) at the cost of Inter-Token Latency (ITL)." Pointer: "Routing Behavior".
7. **Prefix-Cache Aware Routing**
   - Source type: docs
   - URL: <https://github.com/cncf/testing-llm-d/blob/main/docs/architecture/advanced/kv-management/prefix-cache-aware-routing.md>
   - Technique: Route follow-up or shared-prefix requests to replicas likely to hold the relevant KV prefix, using either lightweight rolling-hash approximation or precise token/KV-event indexing. This is highly aligned with multi-turn agentic workloads, where preserving cache locality lowers TTFT.
   - Evidence: Quote: "builds a rolling hash chain". Pointer: Approximate Implementation, "How it Works".
8. **Introducing New KV Cache Reuse Optimizations in NVIDIA TensorRT-LLM**

   - Technique: Expose per-request KV retention hints and consume KV cache events so routing and eviction favor reusable prefixes such as system prompts, tool scaffolds, or conversation history. The engine front-end could propagate priority/duration hints for cache blocks to reduce repeated prefills.
   - Evidence: Quote: "Users can specify two attributes that guide block eviction: priority and duration." Pointer: section "Priority-based KV cache eviction".

   - Source type: paper
   - URL: <https://arxiv.org/abs/2407.00023>
   - Technique: Use distributed prompt scheduling that jointly optimizes prefix-cache reuse and load balance, rather than routing only by load. The engine coordinator could adapt this to keep multi-turn/shared-prompt traffic cache-local without overloading one worker.
   - Evidence: Quote: "co-optimizes KV state reuse and computation load-balancing". Pointer: arXiv abstract.
10. **SGLang v0.4: Zero-Overhead Batch Scheduler, Cache-Aware Load Balancer, Faster Structured Outputs**

   - Evidence: Quote: "The scheduler runs one batch ahead and prepares all the metadata required for the next batch." Pointer: section "Zero-Overhead Batch Scheduler".

   - Evidence: Quote: "KVCache-centric global cache and a scheduler designed to maximize throughput". Pointer: Abstract.

   - Evidence: Quote: "MemServe introduces MemPool, an elastic memory pool managing distributed memory and KV caches across serving instances." Pointer: arXiv abstract.

   - Evidence: Quote: "enable preemption at the granularity of each output token". Pointer: arXiv abstract.

   - Evidence: Quote: "predict the relative ranks of output lengths in a batch of requests". Pointer: OpenReview abstract.

   - URL: <https://openreview.net/forum?id=DOZiCWyK0N>

   - Evidence: Quote: "extend the adaptive prefix-aware scheduler of Preble to account for output length". Pointer: OpenReview abstract.
