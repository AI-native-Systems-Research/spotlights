## Findings (full list)

1. **SGLang v0.4: Zero-Overhead Batch Scheduler, Cache-Aware Load Balancer, Faster Structured Outputs**
   - Source type: blog
   - URL: <https://www.lmsys.org/blog/2024-12-04-sglang-v0-4/>
   - Technique: Adopt one-batch-ahead execution: prepare the next batch's scheduling metadata while workers execute the current GPU batch, using dependency tokens/events to keep correctness. This could reduce executor-side CPU/control-plane gaps between decode iterations, improving median TPOT especially for short agentic turns where per-step overhead is visible.
   - Evidence: Quote: "The scheduler runs one batch ahead and prepares all the metadata required for the next batch." Pointer: Zero-Overhead Batch Scheduler section.
2. **Ray Compiled Graph (beta)**
   - Source type: docs
   - URL: <https://docs.ray.io/en/latest/ray-core/compiled-graph/ray-compiled-graph.html>
   - Technique: Use a static compiled Ray graph for the repeated distributed inference step instead of per-token eager actor orchestration. The transferable idea is to preallocate actor resources, prebuild communication paths, and invoke the same fanout graph with sub-millisecond overhead, reducing Ray backend contribution to TTFT and TPOT.
   - Evidence: Quote: "Less than 50us system overhead for workloads that repeatedly execute the same task graph." Pointer: Ray Compiled Graph overview.
3. **TD-Pipe: Temporally-Disaggregated Pipeline Parallelism Architecture for High-Throughput LLM Inference**
   - Source type: paper
   - URL: <https://arxiv.org/abs/2506.10470>
   - Technique: Adapt temporally disaggregated pipeline execution: run longer prefill and decode epochs with explicit switching decisions instead of frequently mixing phases through the pipeline. Its hierarchy-controller and inter-batch work-stealing ideas fit an executor that coordinates pipeline workers and could reduce pipeline bubbles that inflate TPOT.
   - Evidence: Quote: "disaggregates the prefill and decode phases in the temporal dimension." Pointer: Abstract, arXiv:2506.10470.
4. **SpecPipe: Accelerating Pipeline Parallelism-based LLM Inference with Speculative Decoding**
   - Source type: paper
   - URL: <https://arxiv.org/html/2504.04104v2>
   - Technique: Use pipeline-aware speculative decoding to keep pipeline stages filled with speculative tokens from a dynamic token tree. For pipeline-parallel deployments, the executor could coordinate speculative token work as pipeline microsteps to reduce time between output tokens.
   - Evidence: Quote: "fills the pipeline with speculative tokens of a request step-by-step." Pointer: Abstract, arXiv:2504.04104v2.
5. **Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve**
   - Source type: paper
   - URL: <https://www.usenix.org/conference/osdi24/presentation/agrawal>
   - Technique: Use chunked-prefill plus stall-free batching: split large prefills into similarly sized chunks and interleave them with ongoing decodes. The executor-side implication is support for smooth multi-batch fanout and pipeline filling so prefills do not pause decode traffic, improving TTFT without hurting median TPOT.
   - Evidence: Quote: "chunked-prefills which splits a prefill request into near equal sized chunks." Pointer: USENIX OSDI '24 abstract.
6. **DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving**
   - Source type: paper
   - URL: <https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin>
   - Technique: Separate prefill and decode onto different worker pools with phase-specific resource allocation and placement. An executor could expose phase-specialized process/Ray worker groups and bandwidth-aware placement to independently optimize TTFT and TPOT for multi-turn workloads.
   - Evidence: Quote: "DistServe assigns prefill and decoding computation to different GPUs, hence eliminating prefill-decoding interferences." Pointer: USENIX OSDI '24 abstract.
7. **Deploying DeepSeek with PD Disaggregation and Large-Scale Expert Parallelism on 96 H100 GPUs**
   - Source type: blog
   - URL: <https://www.lmsys.org/blog/2025-05-05-large-scale-ep/>
   - Technique: Apply two-batch overlap for distributed inference: split a batch into two microbatches so compute and communication phases overlap. This could inform executor-level support for multiple in-flight microbatches across distributed workers, reducing communication stalls that show up as TPOT.
   - Evidence: Quote: "TBO splits a single batch into two micro-batches, allowing computation and communication to overlap." Pointer: Two-batch Overlap discussion in Parallelism Design.
8. **Placement Groups**
   - Source type: docs
   - URL: <https://docs.ray.io/en/latest/ray-core/scheduling/placement-group.html>
   - Technique: Use role-aware Ray placement groups to gang-schedule and topology-pack high-communication worker sets while spreading lower-coupling groups. Refining worker placement by TP/PP/phase communication patterns could reduce cross-node latency and improve median TPOT.
   - Evidence: Quote: "schedule Ray tasks and actors packed together for locality (PACK), or spread apart (SPREAD)." Pointer: Ray Placement Groups overview.
9. **msgspec**
   - Source type: docs
   - URL: <https://jcristharif.com/msgspec/>
   - Technique: Replace generic pickle/cloudpickle envelopes on hot executor paths with schema-based MessagePack/msgspec structs, keeping generic callable RPC only for cold control operations. Faster structured serialization can lower CPU overhead when broadcasting scheduler metadata and collecting outputs every decode step.
   - Evidence: Quote: "encoding/decoding a message with msgspec can be ~10-80x faster than alternative libraries." Pointer: msgspec Highlights section.
10. **Limiting Concurrency Per-Method with Concurrency Groups**
   - Source type: docs
   - URL: <https://docs.ray.io/en/latest/ray-core/actors/concurrency_group_api.html>
   - Technique: Use Ray actor concurrency groups to isolate long-running serving work from control, health, or initialization methods. This could make the Ray executor less prone to control-plane head-of-line blocking during hot inference loops, improving responsiveness and failure handling without perturbing decode execution.
   - Evidence: Quote: "methods to be separated into concurrency groups, each with its own thread(s)." Pointer: Ray concurrency groups overview.
11. **Pattern: Using ray.wait to limit the number of pending tasks**
   - Source type: docs
   - URL: <https://docs.ray.io/en/master/ray-core/patterns/limit-pending-tasks.html>
   - Technique: Apply explicit backpressure to non-blocking distributed submissions so the executor caps in-flight work at the useful concurrency window. This can avoid queue buildup and stale pending work under bursty multi-turn agentic traffic, protecting median latency while preserving throughput.
   - Evidence: Quote: "apply backpressure and limit the number of pending tasks." Pointer: Ray design pattern overview.
